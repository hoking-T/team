# 11月17日需求核对与待验收清单

今天讨论中发现，供应商是入库流程里缺少的一环：只有商品和数量，还不能回答“这批货是谁供的”。先把规则和验收步骤记下来，等队友的新版本确定后再接入，避免两边同时改代码。

## 供应商先做到什么程度

- 资料包括编号、名称、联系人、电话；编号和名称必填，联系方式选填。
- 支持新增、查询、修改资料和停用。编号不重复，保存后作为稳定标识，不随名称一起修改。
- 新入库要选择有效供应商；停用后不能用于新入库，但以前的入库记录不能删除。
- 入库记录保存供货方编号和当时的名称，避免供应商改名后看不清原始记录。
- 旧入库没有登记供应商的，显示“历史记录未登记供应商”，不随便补一个名字。
- 暂时不做采购合同、付款和结算，把供货来源与库存业务先连起来。

## 功能需求和非功能需求分开写

“能维护供应商、入库时选择供应商”是功能需求。

“写入单据和增加库存要一起成功或一起失败”“停用和入库同时发生时不能绕过校验”“升级不能破坏历史数据”是非功能要求，需要对应的验证，不能只在报告里写几个形容词。

性能指标要说明测试数据量和环境。没有测过，就先标为目标；短时间演示不能证明100人长期稳定使用或99.5%的可用率。

## 下一轮整合顺序

1. 队友交付新的代码后，确认最终后端语言和启动方法。当前主分支已有Python代码，但仓库首页仍写Java，需要一起核对；如果课程已经登记Java，也需要确认是否允许调整。
2. 先跑通队友版本，再逐项确认哪些功能已有、哪些缺少。今天本地Java版本的功能与测试结果，不能直接当作Python版本的结果。
3. 依据这份规则补缺项，不把Java后端或旧前端直接覆盖到新版本里。数据库升级前先备份，保留真实的原始数据。
4. 最后统一报告里的技术栈、功能范围、表结构、用例图和测试结果。先以实际程序为准，再修改报告，避免两份说明互相矛盾。
