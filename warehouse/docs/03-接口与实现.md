# 三、接口与原型实现

## HTTP接口约定
本机 http://127.0.0.1:8080，JSON UTF-8，同源前后端，无CORS需求。所有写请求Content-Type:application/json。当前成功均200；创建响应为小写id，数据库查询字段为大写（JDBC默认），前端按此读取。错误统一 `{ "message": "中文原因" }`，400输入、404不存在、409冲突、500处理失败。没有身份认证，服务仅本机。

|方法与路径|输入|输出/规则|
|---|---|---|
|GET /api/products|无|数组：ID,CODE,NAME,UNIT|
|POST /api/products|code,name,unit|{id:1}，编号大写归一且唯一|
|GET /api/locations|无|ID,CODE|
|GET /api/stocks|可选productId|PRODUCT_ID,CODE,NAME,UNIT,LOCATION,QUANTITY|
|POST /api/inbounds|productId,locationId,quantity|{id:1}；累加并存入库单|
|GET /api/inbounds|无|ID,PRODUCT_ID,LOCATION_ID,QUANTITY,CREATED_AT,NAME,LOCATION|
|POST /api/orders|productId,locationId,quantity|{id:1}；不扣库存|
|GET /api/orders|无|订单字段及NAME,LOCATION|
|POST /api/orders/{id}/ship|{}|{message:出库成功…}；原子扣减并生成物流|
|GET /api/shipments|无|ID,ORDER_ID,STATUS,NAME,QUANTITY|
|GET /api/shipments/{id}/tracking|无|ID,SHIPMENT_ID,STATUS,CREATED_AT，按时间及ID升序|
|POST /api/shipments/{id}/advance|{status:"TRANSIT"}或{status:"DELIVERED"}|{message:物流状态已更新}|
|GET /api/events|无|EVENT_ID,EVENT_TYPE,AGGREGATE_ID,DETAILS,CREATED_AT|

示例入库：`{"productId":1,"locationId":1,"quantity":100}`；数量必须JSON整数1—1000000（禁止小数截断），ID正整数且引用存在。商品编号1—40位字母数字_-，名称1—100字符且非空白，单位1—20字符且非空白。未知物流目标400，合法目标但不相邻409。

## 模拟物流API协议和调用关系
网页 POST订单出库→OrderService发布ORDER_SHIPPED→EventHandlers同步订阅→LogisticsService.createForOrder(orderId)→数据库生成shipment和WAITING轨迹。创建物流是内部Java接口，不开放任意用户“给未出库订单建物流”的HTTP接口。内部输入long orderId，成功void，已有物流直接返回，失败抛异常。
外部演示接口是上述shipments列表、tracking查询、advance推进。调用例：物流单7处于WAITING，POST `/api/shipments/7/advance` 输入 `{"status":"TRANSIT"}`，200后查询轨迹得到WAITING与TRANSIT；再次同样调用409。再传DELIVERED成功。不是实时快递回调、没有运单供应商、没有真实位置。
事件协议：DomainEvent(id UUID,type字符串,aggregateId long,details摘要)。ORDER_CREATED、ORDER_SHIPPED、STOCK_SHIPPED的aggregateId是订单ID；STOCK_RECEIVED是入库单ID。事件通过应用进程内传递，event_log保存处理审计。跨服务版本化协议属于未来扩展。

## 原型说明
工作台显示从数据库计算的商品数、库存总量、待出库数、在途数和最近事件。商品资料页录入与列表；入库页包含表单、库存筛选和入库记录；出库页展示待出库按钮及状态；物流页提供有序轨迹和相邻状态按钮。错误用页面顶部中文提示，提交按钮在等待期间禁用，数据加载失败不伪造成功。
截图与实测记录放docs/evidence，截图只证明对应时刻操作，不替代并发/事务测试。尚无拣选、盘点页面。

## 代表性核心代码
1. `OrderService.ship` 中 `UPDATE stock SET quantity=quantity-? ... AND quantity>=?` 由数据库原子执行，返回0说明不够。不能先读库存再在Java里减后写回，否则并发可能丢更新。订单FOR UPDATE阻止同一订单双扣，不同订单通过库存行锁竞争。
2. `EventHandlers.handle` 中 `@EventListener @Transactional(propagation=MANDATORY)` 配合 `publishEvent`，保证同步监听器参与出库事务。审计、物流、库存、订单要么一起成功，要么全回滚。事件解耦了订单与物流控制类，但不是异步微服务。
3. `LogisticsService.advance` 对WAITING→TRANSIT、TRANSIT→DELIVERED做严格判断，并把状态更新与tracking插入放一个事务；数据库唯一(shipment_id,status)防重。

答辩建议：用一次出库逐行解释事务，再说明为何“创建订单不扣库存”、为什么需要两类锁、事件失败如何恢复、H2文件在哪里、为什么本版不能接公网。组员必须实际阅读和修改后再陈述自己的贡献。
