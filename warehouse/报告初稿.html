非功能需求

正确性：库存始终0—10亿，单次数量1—100万；同订单只扣一次；原子事务维护一致性。可靠性：文件持久化、失败回滚、重试可判断已出库；备份须停服务复制data目录。可维护性：模块包、统一校验、中文错误、自动化回归。易用性：中文导航、空态、错误反馈、禁止提交期间重复点击。性能目标：教学规模1000条记录下普通操作期望2秒内，尚无负载测试保证；当前列表无分页，后续再优化。安全边界：SQL参数化、页面转义、默认本机监听；未做鉴权/CSRF防护和正式渗透测试，不用于生产。可移植性：实测Windows/JDK25；其他系统和数据库尚待复测。

二、设计规格说明书

架构比较

方案 开发/部署成本 一致性 事件特点 结论
模块化单体+同步进程内事件 一个Java服务、一份数据库，适合5人初学组 同一数据库事务强一致 真实publishEvent/EventListener，无独立队列 采用
微服务+消息队列+独立数据库 多个服务、队列、部署及调试，学习成本高 需Outbox、重试、幂等、最终一致 异步跨服务，适合扩容 超出首版范围

Spring Boot 3.5.7 / Spring MVC / JDBC / H2 2.3.232（由依赖管理锁定）/ Bean Validation / JUnit5；前端原生HTML、CSS、JS，fetch连接后端。不引入Node构建，适合阅读；未采用Bootstrap并不影响基本网页实现。pom声明Java17语言级别，本机运行JDK25.0.1。 逻辑包图04-packages；部署图05-deployment。浏览器HTTP→控制器→模块服务→JDBC→文件数据库；服务发布事件，监听器调用物流。物联网以虚线“未来”展示：扫码枪/传感器→网关→未来设备接入适配器，不冒充已有硬件集成。

事务、并发与事件

  • CatalogService.create 建商品并为所有预置货位建零库存行，一个事务内完成，避免首次入库并发插入同键。
  • InventoryService.receive 原子UPDATE累加，带上限条件；随后写入库单及STOCK_RECEIVED事件审计。
  • OrderService.create仅建PENDING订单，发布ORDER_CREATED，不预占库存。
  • OrderService.ship首先SELECT FOR UPDATE锁订单，检查PENDING；条件UPDATE quantity>=需求扣减，再改SHIPPED；发布STOCK_SHIPPED与ORDER_SHIPPED。
  • EventHandlers为同步@EventListener，MANDATORY要求已有事务；存event_log后处理物流生成。没有@Async，也不是提交后监听。监听失败不吞异常，由Spring回滚库存、订单、事件、物流及轨迹。故障排除后重试确认出库即可。
  • LogisticsService.createForOrder锁同一订单，检查SHIPPED和已有物流，order_id唯一约束兜底；初始轨迹WAITING。advance锁物流，验证相邻状态，更新与轨迹同事务。
  • 同一事件ID顺序重放直接返回；新事件ID也通过订单锁与唯一物流约束避免重复生成。相同事件ID并发重放可能发生唯一键冲突，失败事务需重试，不保证每个并发请求都成功返回；不会产生重复业务结果。
  • 事件记录不是待投递队列：进程崩溃未提交则整体撤销，已提交则业务与审计一起保存。本版没有后台自动重试或跨进程投递。接真实物流时不应在数据库事务内长时间等待外网，应改事务Outbox+异步重试+接收端幂等，属于后续设计。
  • 入库和创建订单没有客户端幂等请求键，网络中断导致结果不明时先查询记录再重试；页面刷新失败会提示核对，不能承诺所有HTTP重试都是幂等。

数据库设计

类→表；库存为商品和货位的关联实体，复合主键；订单和物流1:0..1使用唯一外键；物流和轨迹1:N。实际初始化源 src/main/resources/schema.sql，只建不存在的表和货位，不删除业务数据。无自动迁移工具；修改已有表结构须新增迁移方案，不能指望CREATE IF NOT EXISTS更新旧表。

三、接口与原型实现

HTTP接口约定

本机 http://127.0.0.1:8080，JSON UTF-8，同源前后端，无CORS需求。所有写请求Content-Type:application/json。当前成功均200；创建响应为小写id，数据库查询字段为大写（JDBC默认），前端按此读取。错误统一 { "message": "中文原因" }，400输入、404不存在、409冲突、500处理失败。没有身份认证，服务仅本机。

模拟物流API协议和调用关系

网页 POST订单出库→OrderService发布ORDER_SHIPPED→EventHandlers同步订阅→LogisticsService.createForOrder(orderId)→数据库生成shipment和WAITING轨迹。创建物流是内部Java接口，不开放任意用户“给未出库订单建物流”的HTTP接口。内部输入long orderId，成功void，已有物流直接返回，失败抛异常。 外部演示接口是上述shipments列表、tracking查询、advance推进。调用例：物流单7处于WAITING，POST /api/shipments/7/advance 输入 {"status":"TRANSIT"}，200后查询轨迹得到WAITING与TRANSIT；再次同样调用409。再传DELIVERED成功。不是实时快递回调、没有运单供应商、没有真实位置。 事件协议：DomainEvent(id UUID,type字符串,aggregateId long,details摘要)。ORDER_CREATED、ORDER_SHIPPED、STOCK_SHIPPED的aggregateId是订单ID；STOCK_RECEIVED是入库单ID。事件通过应用进程内传递，event_log保存处理审计。跨服务版本化协议属于未来扩展。

原型说明

工作台显示从数据库计算的商品数、库存总量、待出库数、在途数和最近事件。商品资料页录入与列表；入库页包含表单、库存筛选和入库记录；出库页展示待出库按钮及状态；物流页提供有序轨迹和相邻状态按钮。错误用页面顶部中文提示，提交按钮在等待期间禁用，数据加载失败不伪造成功。 截图与实测记录放docs/evidence，截图只证明对应时刻操作，不替代并发/事务测试。尚无拣选、盘点页面。

代表性核心代码

  1. OrderService.ship 中 UPDATE stock SET quantity=quantity-? ... AND quantity>=? 由数据库原子执行，返回0说明不够。不能先读库存再在Java里减后写回，否则并发可能丢更新。订单FOR UPDATE阻止同一订单双扣，不同订单通过库存行锁竞争。
  2. EventHandlers.handle 中 @EventListener @Transactional(propagation=MANDATORY) 配合 publishEvent，保证同步监听器参与出库事务。审计、物流、库存、订单要么一起成功，要么全回滚。事件解耦了订单与物流控制类，但不是异步微服务。
  3. LogisticsService.advance 对WAITING→TRANSIT、TRANSIT→DELIVERED做严格判断，并把状态更新与tracking插入放一个事务；数据库唯一(shipment_id,status)防重。

答辩建议：用一次出库逐行解释事务，再说明为何“创建订单不扣库存”、为什么需要两类锁、事件失败如何恢复、H2文件在哪里、为什么本版不能接公网。组员必须实际阅读和修改后再陈述自己的贡献。
